1Il viaggio in una figura

Una feature "completa" in un'app Nuxt attraversa quasi sempre gli stessi strati. Quando ne aggiungi una, conviene percorrerli in quest'ordine: dal basso (dove vivono i dati) verso l'alto (dove li vede l'utente).

L'idea chiave

In Nuxt client e server stanno nello stesso progetto, ma restano due programmi diversi che si parlano solo via HTTP. La cartella shared/ è il "contratto" che entrambi leggono, così non possono disallinearsi.

2Passo 1 · Il database

Prima di tutto la colonna. In PetDuel una colonna nuova si scrive in due posti dello stesso file:

server/db/schema.ts Drizzle
// 1. La descrizione per TypeScript e per le query di Drizzle
hideFromRankings: boolean('hide_from_rankings').notNull().default(false),

// 2. L'SQL che crea davvero la colonna, dentro CREATE_TABLES_SQL
ALTER TABLE pets ADD COLUMN IF NOT EXISTS hide_from_rankings boolean NOT NULL DEFAULT false;

Perché due volte? La riga 1 non tocca il database: dice solo a Drizzle "esiste questa colonna, è un booleano". Così pets.hideFromRankings ha il tipo giusto in tutto il codice. La riga 2 è quella che la crea.

Perché IF NOT EXISTS? useDb() in server/utils/db.ts esegue tutto CREATE_TABLES_SQL a ogni avvio del server. Il database esistente ha già i tuoi pet. IF NOT EXISTS rende l'istruzione "idempotente": la prima volta aggiunge la colonna, le volte dopo non fa nulla. È una migrazione fatta a mano, semplice ma efficace per un progetto piccolo.

Perché DEFAULT false? I pet già presenti ricevono subito un valore. Senza default, NOT NULL fallirebbe sulle righe esistenti.

Due nomi: nel database si usa hide_from_rankings (snake_case, la convenzione SQL), in TypeScript hideFromRankings (camelCase). Drizzle traduce. Nelle query SQL scritte a mano vedrai il primo, in quelle Drizzle il secondo.

// server/utils/db.ts: il trucco del "una volta sola"
export async function useDb() {
  ready ??= (async () => {
    await client.exec(schema.CREATE_TABLES_SQL)
    ...
  })()
  await ready
  return db
}

??= assegna solo se ready è ancora vuoto. La prima chiamata avvia la preparazione; le altre, anche se arrivano nello stesso istante, aspettano la stessa Promise invece di rifarla.

3Passo 2 · Il contratto in shared/

shared/models.ts Zod
export const adoptionFieldsSchema = z.object({
  status: z.enum(ADOPTION_STATUS).nullable(),
  sex: z.enum(PET_SEX).nullable().default(null),
  ...
  hideFromRankings: z.boolean().default(false),
})
export type AdoptionFields = z.infer<typeof adoptionFieldsSchema>

Uno schema, tre usi. Il componente lo usa per controllare il form prima di inviarlo. L'endpoint lo usa per rifiutare dati sbagliati. z.infer ne ricava il tipo TypeScript AdoptionFields, così il form reattivo è tipizzato senza scrivere un'interfaccia a parte.

.default(false) rende il campo facoltativo in ingresso. Una vecchia versione della pagina, ancora aperta in qualche browser, che non manda hideFromRankings continua a funzionare. Aggiungere campi con un default è il modo di cambiare un'API senza rompere chi la usa.

Da Vue a Nuxt

In un progetto Vue classico questo file lo dovresti duplicare nel backend, o pubblicarlo come pacchetto. Nuxt 4 dà alla cartella shared/ l'alias #shared, importabile sia da app/ sia da server/. Unica regola: lì dentro niente codice che funziona solo nel browser o solo su Node.

4Passo 3 · Il form nel componente

app/components/AdoptionCard.vue componente
const form = reactive<AdoptionFields>({ status: null, ..., hideFromRankings: false })

function startEdit() {
  const a = info.value
  Object.assign(form, a
    ? { status: a.status, ..., hideFromRankings: a.hideFromRankings }
    : { status: 'available', ..., hideFromRankings: false })
  editing.value = true
}
<label v-if="form.status" class="check">
  <input v-model="form.hideFromRankings" type="checkbox">
  <span><b>Tienilo fuori da classifiche e sfide</b>...</span>
</label>

Il form è una copia. startEdit copia i dati salvati dentro form. Se modificassi direttamente props.pet, cliccare "Annulla" non annullerebbe nulla, e Vue ti avviserebbe che le props non si modificano. La copia si butta via con "Annulla" o si invia con "Salva".

Object.assign e non form = {...}: form è un reactive. Se lo riassegni, il template resta collegato all'oggetto vecchio. Sovrascrivere le proprietà mantiene lo stesso oggetto reattivo.

v-if="form.status": se lo stato è "Nessuna scheda", l'opzione non ha senso e la casella sparisce. È solo un aiuto per l'utente: la regola vera la impone il server (passo 4).

5Passo 4 · L'endpoint

server/api/pets/[id]/adoption.put.ts Nitro
const paramsSchema = z.object({ id: z.coerce.number().int().positive() })

export default defineEventHandler(async (event) => {
  const { user } = await requireShelter(event)
  const { id } = await getValidatedRouterParams(event, paramsSchema.parse)
  const parsed = adoptionFieldsSchema.safeParse(await readBody(event))
  if (!parsed.success) throw createError({ statusCode: 400, statusMessage: ... })

  const db = await useDb()
  const { status, ...fields } = parsed.data
  // Senza scheda di adozione l'opzione non ha senso: il pet torna in gara
  const [pet] = await db.update(pets)
    .set({ adoption: status, ...fields, hideFromRankings: status !== null && fields.hideFromRankings })
    .where(and(eq(pets.id, id), eq(pets.ownerId, user.id)))
    .returning({ id: pets.id })
  if (!pet) throw createError({ statusCode: 404, statusMessage: 'Pet non trovato' })
  return { ok: true }
})

Il nome del file è l'indirizzo. server/api/ + pets/[id]/adoption + .put diventa PUT /api/pets/:id/adoption. Le parentesi quadre sono un parametro, come nelle pagine. Il suffisso .put fa rispondere il file solo a quel metodo HTTP; con un GET Nitro risponde 405.

Da dove arrivano requireShelter, useDb, createError? Nessun import. Nitro importa da solo tutto ciò che esporti in server/utils/ e le sue funzioni (defineEventHandler, readBody, …). Gli import espliciti servono solo per librerie esterne (drizzle-orm, zod) e per lo schema.

Ordine dei controlli: prima chi sei (requireShelter: 401 se non loggato, 403 se non sei un rifugio approvato), poi cosa mandi (Zod). Così uno sconosciuto non scopre nemmeno quali campi esistono.

Rivalidare sul server è obbligatorio. Il controllo nel browser si scavalca con una riga in console: io l'ho fatto apposta nei test, con fetch('/api/pets/133/adoption', { method: 'PUT', ... }). Il server non si fida mai del client.

La sicurezza è nel where. eq(pets.ownerId, user.id) fa sì che un rifugio possa modificare solo i suoi pet. Se il pet è di un altro, l'update non tocca nessuna riga, returning restituisce una lista vuota e rispondiamo 404. Rispondere "non trovato" invece di "non è tuo" non rivela che quel pet esiste.

status !== null && fields.hideFromRankings: la regola di business vive qui, non nel form. Se il rifugio toglie la scheda, il flag si azzera da solo, qualunque cosa abbia mandato il browser.

6Passo 5 · Un filtro riusabile

Salvare il flag è metà del lavoro. L'altra metà è rispettarlo ovunque: ogni query che produce una classifica o una sfida deve escludere quei pet. Per non ripetere la condizione, è diventata una variabile:

server/utils/pets.ts
// In classifiche e sfide entrano tutti, tranne i pet che un rifugio ha scelto di tenere fuori
export const inRankings = sql`not ${pets.hideFromRankings}`

È un frammento SQL di Drizzle: non un risultato, ma un pezzo di query da incastrare in altre query. ${pets.hideFromRankings} diventa il nome della colonna giusto. Essendo in server/utils/, è disponibile ovunque nel server senza import, come hasApprovedPhoto lì accanto.

Ecco dove l'ho dovuto infilare. Trovare questa lista è il vero lavoro: l'ho fatta cercando nel progetto ogni query su pets che ordina per Elo o legge le iscrizioni.

FileCosa protegge

api/pets/[id].get.ts"3° tra i gatti" nella pagina del pet

Due stili di query, stessa idea

Dove la query è scritta con Drizzle (.where(and(..., inRankings))) si usa il frammento. In leaderboard.get.ts la query è SQL scritto a mano con l'alias p, quindi la condizione è scritta per esteso: and not p.hide_from_rankings. Il frammento produrrebbe "pets"."hide_from_rankings", che lì non esiste perché la tabella si chiama p.

Nota cosa non ha il filtro: i duelli normali in home. Era una scelta precisa: il pet resta votabile e visibile, perché la visibilità aiuta l'adozione. Esce solo dalle gare.

7Passo 6 · Difesa su due livelli

L'iscrizione alle sfide è protetta due volte, e non è un doppione:

app/components/ChallengeJoin.vue livello 1 · comodità
const eligible = computed(() => {
  const entered = new Set(props.challenge.myEntries.map(e => e.petId))
  return (profile.value?.pets ?? []).filter(p =>
    !entered.has(p.id) && !p.adoptionInfo?.hideFromRankings && ...)
})

Il pet non compare proprio nella tendina. L'utente non può sbagliare e non vede un errore inutile.

server/api/challenges/[slug]/entries.post.ts livello 2 · regola
if (pet.hideFromRankings) {
  throw createError({ statusCode: 400, statusMessage: 'Hai scelto di tenere questo pet fuori da classifiche e sfide' })
}

Il server rifiuta comunque. Serve per chi chiama l'API direttamente, ma anche per una pagina rimasta aperta da prima che il rifugio cambiasse l'opzione.

Regola d'oro

Il client nasconde, il server impedisce. Se devi scegliere dove mettere un controllo, mettilo sempre sul server; quello nel client è un regalo all'esperienza utente.

8Passo 7 · Il ritorno in pagina

Il rifugio clicca "Salva", l'API risponde { ok: true }. Come fa la pagina a mostrare il dato nuovo?

// AdoptionCard.vue: avvisa il genitore e basta
await $fetch(`/api/pets/${props.pet.id}/adoption`, { method: 'PUT', body: check.data })
editing.value = false
emit('changed')

// pages/pet/[id].vue: il genitore ricarica
const { data: pet, refresh } = await useFetch(...)
<AdoptionCard :pet="pet" :manage="manage" @changed="refresh()" />
  1. Il componente non aggiorna i dati da solo: non è lui il proprietario di pet. Emette changed, il classico pattern Vue "props giù, eventi su".
  2. La pagina chiama refresh(), la funzione che useFetch restituisce per ripetere la stessa richiesta. pet.value viene sostituito.
  3. Sul server, GET /api/pets/133 passa da loadAdoptions() in server/utils/shelters.ts, che ora copia anche hideFromRankings dentro adoptionInfo.
  4. Tutto ciò che dipende da pet si ricalcola: la nota "Fuori da classifiche e sfide", la posizione che sparisce, la tendina di ChallengeJoin.
Perché non restituire il pet dalla PUT?

Si poteva, e si risparmia una richiesta. Ma la pagina del pet calcola molte cose (posizione, foto, trofei) in [id].get.ts. Ricaricare da lì garantisce che tutto sia coerente, senza duplicare quella logica nella PUT. Per un'azione rara come questa la richiesta in più non costa nulla.

9I casi limite

Una feature non è finita quando funziona il caso felice. Le domande che mi sono fatto:

  • E se il rifugio chiude, o l'admin lo revoca? I suoi pet tornano privati normali. In shelters/me.delete.ts e admin/shelters/[id].post.ts l'update azzera anche il flag: .set({ adoption: null, hideFromRankings: false }). Altrimenti un pet resterebbe invisibile per sempre, senza più nessun modo di cambiare l'opzione dall'interfaccia.
  • E la card da condividere? Prima compariva solo se il pet aveva una posizione. Un pet fuori classifica non ce l'ha, ma il rifugio vuole condividerlo più di tutti. Ora la condizione è "ha almeno una foto approvata" (isPublic in pages/pet/[id].vue).
  • E il "#1 più amato" in Cerca casa? In adoptables.get.ts la posizione si calcola con una window function: row_number() over (partition by p.hide_from_rankings order by p.elo desc). partition by fa ripartire la numerazione da 1 in ogni gruppo, così i pet nascosti non rubano posizioni agli altri. Poi un case when li mette a null.
  • E i duelli già votati? I voti restano e l'Elo continua a muoversi. Se il rifugio toglie la spunta, il pet rientra con il punteggio aggiornato.

10Due errori di TypeScript, spiegati

Il typecheck me ne ha dati due. Sono istruttivi perché sono trappole comuni.

server/utils/cards.ts errore 1
// Prima: Type '0' is not assignable to type 'string | false | Node | null'
d.speciesRank && pill(`${d.speciesRank}° ...`)
// Dopo
!!d.speciesRank && pill(`${d.speciesRank}° ...`)

In JavaScript a && b non restituisce true o false: restituisce a se è "falsy", altrimenti b. speciesRank ora è number | null, e un numero può essere 0. TypeScript se ne accorge: l'espressione potrebbe valere 0, e satori disegnerebbe un "0" sulla card. !! trasforma prima in booleano, quindi il risultato è false o il nodo.

Lo stesso bug esiste nei template Vue: <span>{{ count && 'nuovi' }}</span> mostra "0". Lì si usa v-if.

app/pages/pet/[id].vue errore 2
// Prima: 'pet.value' is possibly 'undefined'
ogImage: () => (isPublic.value ? `${origin}/card/${pet.value.id}.png` : undefined)
// Dopo
ogImage: () => (isPublic.value && pet.value ? `${origin}/card/${pet.value.id}.png` : undefined)

Noi sappiamo che se isPublic è vero allora pet esiste: isPublic lo controlla dentro. TypeScript no: il narrowing (restringere un tipo dopo un controllo) funziona solo sul controllo che vede in quella stessa espressione, non attraverso un'altra computed. Aggiungere && pet.value glielo dice esplicitamente.

11Quiz

Prova a rispondere prima di aprire.

1. Togli IF NOT EXISTS dall'ALTER TABLE e riavvia due volte il server. Cosa succede?

Il primo avvio aggiunge la colonna. Al secondo Postgres risponde "column already exists", useDb() fallisce e ogni richiesta all'API va in errore 500. Le istruzioni in CREATE_TABLES_SQL devono poter girare infinite volte.

2. Perché adoption.put.ts non ha import { requireShelter } from '../../../utils/shelters'?

Nitro importa da solo tutti gli export di server/utils/ dentro il codice del server. Nel codice di app/ invece non sono disponibili: lì gli auto-import sono quelli di app/composables/ e app/utils/.

3. Un rifugio prova a nascondere il pet di un altro rifugio mandando il suo id. Quale riga lo ferma, e cosa riceve?

.where(and(eq(pets.id, id), eq(pets.ownerId, user.id))): nessuna riga corrisponde, returning è vuoto e riceve 404 "Pet non trovato".

4. Se togliessi il filtro da ChallengeJoin.vue, la feature sarebbe ancora sicura?

Sì: entries.post.ts rifiuta comunque. Peggiorerebbe solo l'esperienza: l'utente vedrebbe il pet nella tendina e riceverebbe un errore dopo aver scelto la foto.

5. Perché AdoptionCard emette changed invece di modificare props.pet.adoptionInfo?

Le props sono in sola lettura: i dati appartengono alla pagina, che li ha caricati con useFetch. Il figlio avvisa, il genitore ricarica dalla fonte, cioè il server, e ottiene anche i valori calcolati lì.

12Esercizio: rifallo tu

Ora tocca a te seguire gli stessi strati. Obiettivo: un proprietario può nascondere la città del suo pet. Molti preferiscono non dire dove vivono.

  • Database: colonna hide_city in schema.ts, in entrambi i posti.
  • Contratto: il campo nello schema Zod che usa la modifica del pet in shared/models.ts (cercalo partendo da server/api/pets/[id].patch.ts).
  • Form: una checkbox nel form di modifica in PetGallery.vue.
  • Endpoint: [id].patch.ts salva il valore. Controlla che la condizione sul proprietario ci sia già.
  • Filtro: dove esce la città? Cercala con la ricerca del tuo editor (city in server/) e decidi dove svuotarla. Suggerimento: toPublicPet in server/utils/db.ts è un buon punto unico.
  • Caso limite: il filtro città di Cerca casa deve continuare a funzionare per i pet dei rifugi? Decidi tu e scrivi un commento che spiega perché.
  • Verifica: npx nuxi typecheck, poi apri la classifica e la pagina del pet.
