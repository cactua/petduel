01Le 7 idee di Nuxt da capire prima

Nuxt è Vue più una serie di convenzioni: metti un file nella cartella giusta e Nuxt sa già cosa farne. Quasi tutto quello che vedrai nel progetto si spiega con queste sette idee.

1. Il nome della cartella decide il ruolo del file

Non registri rotte, componenti o API a mano. Nuxt guarda dove sta il file:

CartellaCosa diventa
app/pages/una pagina con il suo URL (pages/carica.vue → /carica)
app/components/componenti usabili ovunque senza import
app/composables/, app/utils/funzioni usabili ovunque nel client senza import
app/middleware/controlli che girano prima di entrare in una pagina
server/api/endpoint HTTP (api/vote.post.ts → POST /api/vote)
server/routes/endpoint senza il prefisso /api (/img/…, /card/…)
server/utils/funzioni usabili in tutto il server senza import
server/middleware/codice che gira su ogni richiesta al server
server/plugins/codice che gira una volta all'avvio del server
shared/codice importabile sia dal client sia dal server (alias #shared)

2. Auto-import

Per questo nei file vedi ref, computed, useFetch, navigateTo, requireUser, useDb usati senza nessun import. Nuxt genera le dichiarazioni in .nuxt/ così TypeScript le conosce. Gli import espliciti che restano sono per le librerie (drizzle, zod) e per #shared.

3. Due mondi nello stesso progetto: app e server

app/ è Vue: gira nel browser (e una prima volta sul server, vedi il punto 4). server/ è Nitro, il backend Node di Nuxt: non arriva mai al browser, quindi lì stanno database, password e segreti. Si parlano solo via HTTP (/api/...).

4. SSR e hydration

Alla prima visita il server esegue i componenti Vue e manda HTML già pronto (veloce e leggibile da Google e dalle anteprime di WhatsApp). Poi nel browser Vue "si aggancia" a quell'HTML: è l'hydration. Da lì in avanti la navigazione è una normale SPA. Conseguenza pratica: window, document e matchMedia esistono solo dentro onMounted (o con server: false), mai nel corpo di <script setup>.

5. useFetch contro $fetch

  • await useFetch('/api/…') carica i dati per la pagina: durante l'SSR li prende il server, li mette nell'HTML, e il browser non rifà la chiamata. Restituisce ref reattive (data, error, refresh). Se l'URL è una funzione, si ricarica quando cambia.
  • useLazyFetch è uguale ma non blocca la pagina; con server: false parte solo nel browser.
  • $fetch('/api/…', { method: 'POST', body }) è una chiamata singola, da usare nelle azioni (click, invio di un form).

6. Gli handler del server

Ogni file in server/api esporta defineEventHandler(async (event) => …). event è la richiesta: da lì leggi body, parametri, query, cookie. Quello che restituisci diventa la risposta JSON. Per un errore fai throw createError({ statusCode, statusMessage }). Il metodo HTTP sta nel nome del file: .get.ts, .post.ts, .patch.ts, .delete.ts. I parametri tra quadre: [id].get.ts → getRouterParam(event, 'id').

7. Configurazione e segreti

runtimeConfig in nuxt.config.ts dichiara i valori; Nuxt li riempie dalle variabili d'ambiente che iniziano con NUXT_ (es. NUXT_VOTE_SECRET → useRuntimeConfig().voteSecret). Quelli fuori da public restano solo sul server.

Ponte da Vue

Se in un progetto Vue+Vite avevi router/index.js, main.js e un backend Express separato, qui il router è la cartella pages/, main.js è nuxt.config.ts + app.vue, ed Express è server/.

03I file nella radice: config e segreti

package.json

Le dipendenze principali e il perché:

  • nuxt, vue, vue-router: il framework.
  • nuxt-auth-utils: sessione in un cookie cifrato e hash delle password.
  • nuxt-security: header di sicurezza, limite di richieste, limite di dimensione.
  • @electric-sql/pglite + drizzle-orm: PostgreSQL che gira dentro Node (niente da installare) e un ORM tipizzato.
  • zod: validazione dei dati.
  • sharp: elaborazione delle immagini.
  • satori + @resvg/resvg-js: disegnano le card PNG da condividere.

Script: npm run dev (sviluppo con ricarica automatica), build/preview (versione di produzione), postinstall (rigenera .nuxt/ dopo ogni install), make-admin.

nuxt.config.ts

È il "main" dell'applicazione. Sezione per sezione:

modules

Attiva i moduli Nuxt: ognuno aggiunge funzioni auto-importate (es. useUserSession, requireUserSession) e configurazione.

css

Il foglio globale ~/assets/css/main.css, incluso in ogni pagina. ~ punta ad app/.

app.head

Tag <head> di default per tutte le pagine: lingua, viewport, colore della barra del telefono, Google Fonts. Le singole pagine li arricchiscono con useHead e useSeoMeta.

runtimeConfig

Segreto dei voti e configurazione della sessione (30 giorni, cookie SameSite=Lax, Secure in produzione). I valori veri arrivano da .env.

security

Content Security Policy (da dove si possono caricare immagini, font, stili), divieto di essere messi in un iframe, rate limit di 600 richieste ogni 5 minuti per IP, body massimo 100 KB (11 MB per gli upload).

routeRules

Regole per gruppi di URL. Qui: login e registrazione hanno un limite molto più stretto (10 tentativi ogni 15 minuti) contro chi prova password a raffica.

nitro.storage

Definisce uno "storage" di nome uploads che scrive su disco in .data/uploads. Nel codice si usa con useStorage('uploads'): domani lo puoi spostare su S3 cambiando solo il driver qui.

.env · .env.example

NUXT_SESSION_PASSWORD cifra il cookie di sessione, NUXT_VOTE_SECRET firma i duelli, PGLITE_DIR dice dove salvare il database. .env.example è il modello da copiare; .env vero non si committa.

tsconfig.json · .nuxt/

tsconfig.json si limita a rimandare ai quattro tsconfig che Nuxt genera in .nuxt/ (app, server, shared, node): ognuno sa quali auto-import esistono in quel mondo. Non si modifica .nuxt/ a mano: si rigenera.

public/ · .data/ · docs/

public/ serve file statici così come sono (favicon.ico, robots.txt). .data/ contiene il database PGlite e le foto: cancellarla azzera tutto (al riavvio ritornano i pet di esempio). docs/ contiene solo bozze grafiche e questa guida.

scripts/make-admin.mjs script

Script Node da terminale: apre il database e mette role = 'admin' a un utente. Va lanciato a server fermo perché PGlite è un file che un solo processo alla volta può aprire.

scripts/commons/ script

discover.mjs cerca foto di animali con licenza libera su Wikimedia Commons; pets.json è la lista scelta; import.mjs le scarica, le converte in WebP con sharp e scrive server/assets/seed/ con autori e licenze. lib.mjs contiene le funzioni comuni (chiamate all'API, filtro sulle licenze). Si usano raramente, solo per cambiare i pet di esempio.

04shared/: il codice che usano sia server sia browser

Perché esiste

Le stesse regole devono valere nel form (per dare l'errore subito) e nell'API (perché il browser non è affidabile). Scriverle due volte vuol dire, prima o poi, averle diverse. Con shared/ le scrivi una volta e le importi con import … from '#shared/models'.

shared/models.ts
SPECIES, SPECIES_LABEL, SPECIES_ONE, SPECIES_SLUG, SPECIES_EMOJI

La lista delle specie e le sue etichette. as const fa sì che TypeScript conosca i valori esatti, così type Species è 'cane' | 'gatto' | …. La funzione privata pick costruisce le varie mappe da un'unica tabella.

speciesFromSlug(slug)

Da "gatti" (nell'URL) a "gatto".

PERIODS, PHOTO_STATUS, REJECT_REASONS, ADOPTION_STATUS…

Elenchi chiusi di valori: lo stesso schema "array as const + tipo derivato".

registerSchema, loginSchema, petFieldsSchema, challengeFieldsSchema, shelterFieldsSchema, adoptionFieldsSchema, adoptionRequestSchema

Schemi Zod: descrivono la forma dei dati e i messaggi di errore in italiano. Si usano con schema.safeParse(dati), che restituisce { success, data } oppure { success: false, error }. Fanno anche pulizia: .trim(), .toLowerCase(), valori di default.

interface PublicPet, RankedPet, Leaderboard, Duel, PetGallery, Profile, ChallengeDetail…

La forma delle risposte delle API. Il server le usa come tipo di ritorno, il client come tipo di useFetch<…>: se cambi un campo da una parte, TypeScript te lo segnala dall'altra.

shared/images.ts
IMAGE_VARIANTS

Le tre forme di ritaglio: v verticale 3:4, h orizzontale 3:2, s quadrata. Per ognuna le larghezze generate (anche doppie e triple, per gli schermi retina) e dove si usa.

cropSchema, cropsSchema

Un ritaglio è {x, y, w, h} in frazioni dell'immagine (0-1), così non dipende dalla risoluzione.

variantName(image, variant, width, format)

Il nome del file di una variante: abc.webp → abc-h960.avif.

parseImageName(name)

Il contrario: da un nome richiesto all'URL ricava foto, forma, larghezza e formato, rifiutando larghezze non previste (nessuno può farci generare 10.000 misure diverse).

variantSrcset(src, variant, format)

Costruisce l'attributo srcset ("…-v360.avif 360w, …-v720.avif 720w"): il browser sceglie da solo la misura giusta.

centeredCrop(width, height, ratio)

Il ritaglio centrato più grande possibile: si usa quando l'utente non sceglie.

shared/types/auth.d.ts

Estende i tipi di nuxt-auth-utils: dice a TypeScript che session.user ha id, username, role e che la sessione contiene anche voterId e recent. È la tecnica chiamata module augmentation.

05Il database: schema, PGlite, esempi

server/db/schema.ts

Le tabelle descritte con Drizzle. Ogni pgTable('nome', { colonne }) diventa un oggetto TypeScript che usi nelle query (db.select().from(pets)) con autocompletamento e controllo dei tipi.

TabellaContiene
usersaccount: email, username, hash della password, ruolo
petsil pet, il proprietario, Elo, vittorie, sconfitte, scheda di adozione
photosle foto di un pet con stato di moderazione e crediti
votesogni voto: chi, quale coppia, chi ha vinto, quanti punti
challenges, challenge_entries, challenge_votessfide, iscritti con la foto scelta, voti delle sfide
shelters, adoption_requestsrifugi da verificare e richieste di adozione

Dettagli da notare: references(() => users.id, { onDelete: 'cascade' }) fa sparire i figli quando cancelli il padre (elimini un pet → spariscono foto e voti). unique().on(t.voterId, t.pairKey) impedisce a livello di database di votare due volte la stessa coppia. $type<Species>() dice a TypeScript che una colonna text contiene solo certi valori.

CREATE_TABLES_SQL

Lo stesso schema scritto in SQL, eseguito a ogni avvio. Usa CREATE TABLE IF NOT EXISTS e ALTER TABLE … ADD COLUMN IF NOT EXISTS: così aggiungere una colonna non rompe un database esistente. È una "migrazione fatta a mano"; con il progetto più grande si passa a drizzle-kit, che genera le migrazioni da solo.

server/utils/db.ts
useDb()

Il punto d'accesso al database per tutto il server. La prima volta crea le tabelle e, se non ci sono pet, carica gli esempi; le volte dopo restituisce subito la connessione. Il trucco è ready ??= (async () => …)(): la Promise si crea una volta sola e chiunque arrivi dopo aspetta la stessa.

imageUrl(image)

Da nome del file a URL pubblico (/img/…).

photoCredit(text, url), toPublicPet(pet, image, owner, credit)

Trasformano righe del database in oggetti da mandare al browser, scegliendo cosa esporre (mai email, mai id del proprietario).

server/utils/seed.ts
seedPets(db)

Al primo avvio crea l'account tecnico petduel (con hash "!", che non corrisponde a nessuna password) e i pet di esempio, copiando le foto da server/assets/seed nello storage uploads. useStorage('assets:server') legge i file messi in server/assets, che Nitro include nel build.

06Login, sessione e sicurezza

Come funziona la sessione

nuxt-auth-utils salva la sessione in un cookie cifrato con NUXT_SESSION_PASSWORD: il browser lo tiene ma non può leggerlo né modificarlo. Sul server lo leggi con getUserSession(event), lo scrivi con replaceUserSession. Nel client useUserSession() ti dà loggedIn e user, chiedendoli a /api/_auth/session.

server/api/auth/register.post.ts · login.post.ts · logout.post.ts

Registrazione: valida con registerSchema, blocca username riservati e password che contengono username o email, controlla duplicati, salva l'hash con hashPassword (scrypt), apre la sessione. Login: stessa risposta e stesso tempo sia se l'email non esiste sia se la password è sbagliata, così non si scopre chi è iscritto; se l'algoritmo di hash è cambiato, ricalcola l'hash (passwordNeedsReHash). Logout: clearUserSession.

server/utils/auth.ts
requireUser(event)

La prima riga di quasi ogni API protetta. Esige la sessione (altrimenti 401) e rilegge l'utente dal database: un account cancellato o un ruolo tolto valgono subito, non quando scade il cookie.

requireAdmin(event)

Come sopra, più il controllo role === 'admin' (altrimenti 403).

loadSessionUser, isAdmin

Letture veloci dell'utente e del ruolo.

startSession(event, user)

Scrive la sessione dopo login o registrazione, con voterId: "u:<id>".

getDummyHash()

Un hash finto, calcolato una volta, usato nel login quando l'email non esiste (per il trucco del tempo uguale).

server/plugins/session.ts plugin Nitro

defineNitroPlugin gira all'avvio. Qui si aggancia all'evento fetch della sessione: ogni volta che il browser chiede chi è l'utente, il ruolo viene aggiornato dal database. È per questo che, dopo make-admin, a cactua è comparsa la voce Moderazione.

server/middleware/origin.ts middleware server

Gira su ogni richiesta. Per le richieste che modificano dati (POST, PATCH, DELETE su /api) controlla che l'header Origin sia il nostro sito: un altro sito non può farti votare o cancellare cose a tua insaputa (attacco CSRF).

app/middleware/auth.ts · admin.ts middleware di rotta

Girano nel client prima di aprire una pagina che li dichiara con definePageMeta({ middleware: 'auth' }). Se non sei loggato ti mandano ad /accedi?redirect=…. Sono solo una comodità: la vera protezione è sempre sull'API, perché chiunque può chiamare un endpoint senza passare dalla pagina.

07Il cuore: duelli, voti ed Elo

server/utils/ranking.ts
pairKey(a, b)

Una chiave uguale per la coppia (3,8) e (8,3): "3-8". Serve a ricordare le coppie già votate.

eloDelta(winnerElo, loserElo)

Il sistema Elo degli scacchi: calcola quanto era "atteso" che vincesse il vincitore e gli dà 32 × (1 − atteso) punti. Battere un favorito vale molto, battere uno sfavorito quasi niente.

pickPair(pets, voted, recent)

Sceglie la coppia "quasi casuale": stessa specie, Elo vicino, più probabilità a chi ha fatto pochi duelli, quasi mai un pet visto da poco, mai una coppia già votata.

weighted(items, weight)

Estrazione a sorte pesata: ogni elemento ha probabilità proporzionale al suo peso.

server/utils/voter.ts
getVoter(event)

Chi sta votando. Con account: u:<id>. Senza account: un id casuale salvato nel cookie cifrato. Restituisce anche gli ultimi pet visti.

rememberSeen, saveVoter

Aggiornano la lista degli ultimi 8 pet visti nella sessione.

issueDuelToken(voterId, ids, scope)

Quando il server propone una coppia, firma con HMAC un "biglietto" che contiene votante, coppia, ora e ambito (duelli normali o una certa sfida). Il voto deve riportare quel biglietto.

readDuelToken, sign

Verificano la firma (con timingSafeEqual, che non rivela nulla tramite i tempi) e la scadenza di 10 minuti.

readVote(event, scope)

Valida un voto: biglietto valido, dello stesso votante, dello stesso ambito, vincitore che fa parte della coppia, e non più veloce di 300 ms (un umano non ci riesce, un bot sì).

server/api/duel.get.ts

Prende i pet candidati (filtro specie, esclusi i tuoi, solo con foto approvata) e le coppie che hai già votato, chiama pickPair, sceglie una foto a caso per ciascuno (randomApprovedImages) e risponde con i due pet più il biglietto firmato.

server/api/vote.post.ts

Legge il voto con readVote, poi in una transazione (tutto o niente): inserisce il voto con il suo delta Elo (se la coppia era già votata, onConflictDoNothing non inserisce nulla e rispondiamo 409) e sposta i punti tra i due pet. L'aggiornamento è elo = elo + d fatto in SQL, così due voti contemporanei non si sovrascrivono.

08Foto: caricamento, ritagli, varianti

server/utils/photos.ts
readPhotoUpload(event)

Legge un form multipart (readMultipartFormData): campi di testo, file e ritagli scelti. Controlla la dimensione, poi passa il file a sharp che lo raddrizza secondo l'EXIF e lo decodifica: se non è un'immagine vera, fallisce qui. La ricodifica butta via tutto il resto (GPS, metadati, eventuale contenuto nascosto). Infine genera tutte le varianti.

cropRect(crop, width, height, ratio)

Da frazioni a pixel, correggendo gli arrotondamenti per avere esattamente le proporzioni giuste.

renderVariant, encode

Una variante: ritaglia, ridimensiona senza mai ingrandire, codifica in AVIF (qualità 52) o WebP (qualità 78).

writeVariants(image, source, crops)

Genera in parallelo 3 forme × più larghezze × 2 formati, più la foto base 900×1200, e le salva nello storage uploads.

ensureVariant(image, variant, width, format)

Per le foto caricate prima che esistessero i ritagli: genera la variante al primo bisogno, con un ritaglio automatico che cerca il soggetto (sharp.strategy.attention), e la salva per le volte dopo.

assertPendingQuota(userId)

Massimo 10 foto in attesa per utente, per non intasare la coda di moderazione.

removeImage(image)

Cancella la foto base e tutte le sue varianti.

server/routes/img/[name].get.ts

Serve /img/…. Interpreta il nome con parseImageName, cerca la foto nel database e decide chi può vederla: le approvate tutti, le altre solo il proprietario o un moderatore. Le foto pubbliche hanno una cache di una settimana, le private nessuna cache.

app/utils/pictures.ts
photoSources(src, variant, sizes, desktop?)

Produce la lista dei <source> per un <picture>: prima AVIF, poi WebP, ciascuno con srcset e sizes. Con desktop aggiunge un ritaglio diverso sopra i 760px (es. duelli orizzontali su telefono e verticali su computer). Nel template: <source v-for="s in photoSources(...)" v-bind="s">.

Perché picture { display: contents }

Nel CSS globale <picture> "sparisce" dal layout, così le regole scritte per img continuano a funzionare. E picture > source { display: none } serve perché Chrome mostrerebbe i <source> come blocchi vuoti dentro un flex (era il bug della pagina di moderazione).

app/components/PhotoCropper.vue

L'editor dei ritagli. Lo stato per ogni forma è { zoom, cx, cy } (centro del ritaglio in frazioni).

cropOf(v)

Calcola il ritaglio più grande possibile per quelle proporzioni, diviso per lo zoom, tenuto dentro la foto.

settle(v)

Riporta il centro dove il ritaglio è valido, così trascinare oltre il bordo non "accumula" spostamento.

imgStyle(v)

Posiziona la foto dentro la cornice con percentuali: la cornice è il ritaglio.

onDown, onMove, onUp, setZoom, onWheel, reset

Pointer events: un dito o il mouse spostano, due dita fanno il pinch (si confronta la distanza tra le dita), la rotellina zooma. setPointerCapture continua a ricevere il movimento anche se il dito esce dalla cornice.

Con defineModel espone i ritagli come v-model: la pagina li riceve già pronti per il campo crops.

app/composables/usePhotoPaste.ts

Ascolta paste, dragover e drop su tutto il documento e chiama una funzione col primo file immagine. readClipboard usa navigator.clipboard.read() per il pulsante "Incolla" sul telefono. Gli ascoltatori si aggiungono in onMounted e si tolgono in onBeforeUnmount: è la regola d'oro dei composable che toccano il DOM.

app/pages/carica.vue

Il form di caricamento. Con URL.createObjectURL(file) mostra l'anteprima senza caricare nulla; invia un FormData con i campi, la foto e i ritagli in JSON. Se nella query c'è ?pet=12, aggiunge la foto a quel pet invece di crearne uno nuovo.

09Pet, profili e moderazione

server/utils/pets.ts
hasApprovedPhoto, coverImage

Pezzi di SQL riusabili (sql`…` di Drizzle): "ha almeno una foto approvata" e "ultima foto approvata". Si infilano nelle where e nelle select.

randomApprovedImages(petIds)

Una foto approvata a caso per ogni pet, con distinct on di PostgreSQL.

loadGalleries(where, includePrivate)

Carica pet + foto + proprietari + trofei + schede di adozione in poche query parallele (Promise.all) e le ricompone. Con includePrivate il proprietario vede anche le foto in attesa o rifiutate.

publicStats(pet)

I campi del pet che si possono mostrare.

server/api/pets.post.ts · pets/[id]/photos.post.ts

Nuovo pet con la prima foto, oppure nuova foto per un pet esistente. Notare l'ordine: prima readPhotoUpload, poi la validazione dei campi; se i campi sono sbagliati, la foto appena salvata viene cancellata. Pet e foto si inseriscono in una transazione.

server/api/pets/[id].get.ts · [id].patch.ts · [id].delete.ts

Leggere il pet (con la posizione in classifica della sua specie), correggerne i dati, eliminarlo. La condizione eq(pets.ownerId, user.id) dentro la where dell'update fa sì che un altro utente semplicemente non trovi nulla da modificare (404).

server/api/photos/[id].delete.ts · users/[username].get.ts

Togliere una foto (il proprietario o un moderatore) e il profilo pubblico: username, data di iscrizione, rifugio verificato se c'è, pet. Mai l'email.

server/api/admin/photos.get.ts · admin/photos/[id].post.ts

La coda di moderazione (dalla più vecchia) e la decisione. z.discriminatedUnion('action', […]) accetta { action: 'approve' } oppure { action: 'reject', reason }, con il motivo obbligatorio solo nel secondo caso. Una foto rifiutata viene cancellata dal disco.

app/pages/u/[username].vue · pet/[id].vue · admin/moderazione.vue

Le pagine corrispondenti. Il nome tra quadre diventa un parametro: route.params.username. Nella pagina del pet useSeoMeta imposta titolo e immagine di anteprima per WhatsApp e social, che vengono già scritti nell'HTML grazie all'SSR.

10Classifiche e sfide

server/api/leaderboard.get.ts

La query più "SQL" del progetto, da leggere con calma:

  3. Restituisce i primi 50 più i tuoi pet se sono più giù.

13app/: il guscio, lo stile e il routing

app/app.vue

Il componente radice: ogni pagina viene disegnata al posto di <NuxtPage />. Contiene l'header (logo, menu desktop, account, tema), il dock in basso su mobile e <NuxtRouteAnnouncer /> (annuncia il cambio pagina agli screen reader).

logout()

Chiama l'API, aggiorna la sessione nel client, torna alla home.

themeCookie, useHead({ htmlAttrs }), toggleTheme()

Il tema scelto sta in un cookie (non in localStorage) perché il server lo deve leggere per mandare già l'HTML con data-theme giusto: niente lampo di colori sbagliati. useCookie funziona sia sul server sia nel browser.

systemDark, themeReady

Il tema del sistema si conosce solo nel browser (matchMedia in onMounted); fino ad allora l'icona del pulsante resta invisibile.

Dettaglio: .shell:has(.fit-screen) fa stare i duelli esattamente in uno schermo; le altre pagine scorrono normalmente.

Il bug del corallo gigante

Lo stile scoped di app.vue vale anche sull'elemento radice delle pagine (Vue gli passa l'attributo del genitore). La pagina Carica aveva <section class="upload">, come il pulsante "+ Carica" dell'header, e ne prendeva lo stile. Lezione: nei componenti genitori evita classi generiche.

app/assets/css/main.css

I colori sono variabili CSS (--bg, --coral, --action…) definite per il tema chiaro, ridefinite per il tema scuro sotto prefers-color-scheme: dark (se non hai scelto) e sotto [data-theme="dark"] (se hai scelto). I componenti usano solo le variabili, quindi cambiano tema da soli. Poi lo sfondo con le macchie, i font, le regole di base per input e pulsanti.

Il gesto del voto. geometry(i) calcola direzione e distanza verso l'avversario (in verticale su telefono, in orizzontale su computer). onDown/onMove/onUp spostano la card con transform; si vota solo oltre il 40% del percorso, quindi un clic non vota. 15Due viaggi completi, dal tocco al database

Viaggio 1: voti un duello

sequenceDiagram
  participant B as Browser (index.vue)
  participant S as Server Nitro
  participant D as Database
  B->>S: GET /api/duel?species=gatto
  S->>D: pet candidati e coppie già votate
  S-->>B: due pet + biglietto firmato
  Note over B: trascini la card oltre il 40%
  B->>S: POST /api/vote {token, winnerId}
  S->>S: readVote: firma, votante, tempo
  S->>D: transazione: voto + Elo
  S-->>B: { delta: 12 }
  Note over B: toast, poi la coppia già precaricata

Viaggio 2: carichi la foto di un nuovo pet

  1. carica.vue mostra l'anteprima con un URL blob: e apre PhotoCropper; tu scegli i tre ritagli.
  2. All'invio parte un FormData verso POST /api/pets. Prima ancora di arrivare all'handler: nuxt-security controlla dimensione e rate limit, origin.ts controlla da dove arriva.
  3. L'handler chiama requireUser (chi sei), assertPendingQuota (non troppe foto in attesa), readPhotoUpload (decodifica, ripulisce, genera 21 file).
  4. Valida i campi con lo stesso petFieldsSchema che il form ha già usato, poi inserisce pet e foto (stato pending) in una transazione.
  5. Un moderatore la vede in /admin/moderazione e la approva: da quel momento hasApprovedPhoto è vero e il pet entra in duelli e classifiche.
  6. Quando qualcuno apre il pet, il browser chiede per esempio /img/<id>-v720.avif: routes/img controlla i permessi e serve il file giusto per il suo schermo.

16Esercizi per mettere le mani nel codice

In ordine di difficoltà. Ognuno ti fa toccare una parte diversa.

  1. Una nuova specie ("pesce"). Tocca solo shared/models.ts e guarda quanti posti si aggiornano da soli. Poi aggiungi il colore della medaglietta in DuelArena.vue.
  2. Una pagina "Chi siamo": crea app/pages/chi-siamo.vue e aggiungi il link in app.vue. Usa useHead per il titolo.
  3. Un endpoint server/api/stats.get.ts che restituisce quanti pet e quanti voti ci sono. Usa useDb() e count(*), poi mostralo nella pagina nuova con useFetch.
  4. Una regola nuova: impedisci nomi di pet tutti in maiuscolo. Aggiungila allo schema Zod in shared/ e verifica che il messaggio compaia sia nel form sia chiamando l'API direttamente.
  5. Una classifica per città: aggiungi un parametro city a leaderboard.get.ts (validato con Zod) e un filtro nella pagina, prendendo spunto da adoptables.get.ts.
